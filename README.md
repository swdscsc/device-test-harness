# 设备侧自动化回归测试框架（Device Test Harness）

> 面向**嵌入式 / 硬件公司测试开发岗**的实战项目：用 pytest 从零搭一套跑在**串口 AT 指令**上的
> 自动化回归框架，覆盖协议一致性、负向、边界、**故障注入与恢复**、长稳五个维度，
> 并自研 HTML 报告输出**协议分支覆盖率**与**响应时延分布**。
> **无需硬件即可完整运行**；插上真板子改一个环境变量，同一套用例直接跑在实物上。

---

## 一、为什么做这个项目

校招的"测试开发"作品集几乎全是 **Web 接口测试 + UI 自动化**。但 OPPO / vivo / 比亚迪 /
宇瞳 / 汉邦这类公司的测试岗，主力场景是**设备侧**：固件与上位机之间的串口命令、
协议一致性、异常链路下的恢复能力。这块能力用 Postman 和 Selenium 练不出来，也几乎没人做。

这个项目补的就是这个缺口，而且刻意选了几个"接口测试碰不到、但设备测试必须面对"的问题：

| 设备测试的真问题 | 本项目怎么处理 |
|---|---|
| 设备**不响应**怎么办？是丢包还是设备挂了？ | 故障注入：`drop` 后验证客户端超时判定与重试次数 |
| 设备**答得慢**怎么办？超时阈值定多少合理？ | `slow` 注入 350ms > 客户端 300ms 超时，验证超时路径 |
| 设备**答错对象**怎么办？（串包 / 固件应答张冠李戴） | 客户端校验应答 `tag` 与请求命令是否匹配，不匹配按帧错误处理 |
| 设备**回半截**、回乱码怎么办？ | `truncate` / `garbage` 注入，验证帧完整性校验 |
| 设备**忙**的时候会不会静默丢弃？ | `busy` 注入 `-ERR:5`，验证错误码透传 |
| 链路受扰后**能不能自己恢复**？ | `recover()` 用 `AT` 探测，记录恢复所需轮次 |
| 设备**跑久了会不会变慢/内存涨**？ | 200 轮混合命令长稳，断言时延不劣化 |

## 二、协议设计

刻意做成 **AT 指令风格**，贴近 ESP8266 / 4G 模组 / 各类外设模组的真实交互方式：

```
请求：  AT[+CMD[=ARG]]\r\n
成功：  +CMD:PAYLOAD\r\n
失败：  -ERR:<code>\r\n
```

| 错误码 | 含义 | 触发条件 |
|---|---|---|
| 1 | `UNKNOWN_CMD` | 命令字不在命令表内 |
| 2 | `BAD_PARAM` | 参数无法解析为整数（如 `AT+LED=abc`） |
| 3 | `OUT_OF_RANGE` | 参数超合法区间（`LED∉{0,1}`、`RATE∉[10,1000]`） |
| 4 | `MALFORMED` | 帧结构不合法（非 `AT` 开头、`AT+VER=1` 带了不该有的参数） |
| 5 | `BUSY` | 设备忙 |

**关键设计：合法区间 `RATE_MIN/RATE_MAX`、`LED_VALUES` 只写在 `protocol.py` 一处**，
用例引用它而不是硬编码 10/1000。否则改了协议忘了改用例，测试会"通过但测错东西"。

**分支覆盖率的分母由协议定义，不是由用例定义**：

```python
# protocol.py —— 9 条命令各有 1 条成功路径 + 5 个错误码 + 1 个超时 = 15 条分支
BRANCHES = {(cmd, "ok") for cmd in (...)} | {("*", f"err{e}") for e in ERR} | {("*", "timeout")}
```

这样"覆盖率 15/15"是**协议视角的完备性**，而不是"我写了几个用例就算几个"。新增命令时
分母自动变大，用例没跟上覆盖率就会掉——这是它比普通用例计数更有意义的地方。

## 三、架构：三层分离，后端可插拔

```
protocol.py    协议层：帧构造 / 解析 / 命令表 / 错误码 / 分支清单
    │          （唯一事实来源，设备与用例都引用它）
    ▼
device.py      被测设备：SimDevice（模拟固件，可注入故障）
    │                    SerialDevice（真实串口，需 pyserial）
    │          两者实现同一组接口：write / readline / reset
    ▼
client.py      测试客户端：发命令 / 解析 / 重试 / 时延统计 / 分支记账
    │          （"框架"和"写脚本"的分界线——用例只管业务断言）
    ▼
tests/         用例层：5 个维度 55 条用例
    │
report.py      pytest 插件：会话结束出 HTML 报告 + summary.json
```

**最重要的一个设计：用例代码里没有一处 `if 模拟器 else 真机`。**

```python
# conftest.py
port = os.environ.get("DUT_PORT")
dev = SerialDevice(port, ...) if port else SimDevice(seed=seed, faults=faults)
```

`make_client(faults=[...])` 是统一入口。默认走模拟器（面试官 clone 下来就能跑，
不用等我找板子），`python run.py --port COM3` 就切到真机。
**同一个断言在两种后端下都成立**，才叫"回归测试"；否则只是"跑通脚本"。

## 四、五个测试维度

| 套件 | 用例数 | 测什么 |
|---|---|---|
| `test_01_conformance.py` | 12 | 协议一致性：握手 `AT`、`VER/ID/TEMP/HUMI/STATUS` 正常应答、`LED`/`RATE` 状态可读写回读、`RESET` 后状态归位 |
| `test_02_negative.py` | 12 | 负向：5 个错误码全覆盖、非 AT 帧、空帧、超长帧、命令大小写混写 |
| `test_03_boundary.py` | 参数化 | 边界：`RATE` 取 9/10/1000/1001、`LED` 取 -1/0/1/2、`TEMP` 返回值域校验 |
| `test_04_fault_recovery.py` | 7 | 故障注入：`drop`/`slow`/`truncate`/`garbage`/`wrong`/`busy` 六类，以及链路恢复 |
| `test_05_soak.py` | 2 | 长稳：200 轮混合命令、时延不劣化、`RESET` 后计数器归零 |

合计 **55 条**，全部通过。

几个用例设计上值得说的点：

- **`drop` 用例断言的是"重试次数恰好等于配置值"**，不是"最终失败了"。失败是必然的，
  精确的重试次数才能证明重试策略真的在按配置工作。
- **`wrong` 用例验证应答错位检测**：模拟器故意回 `+VER:9.9.9` 去应答 `TEMP` 请求，
  客户端靠 `EXPECTED_TAG` 发现 tag 不符并抛 `FrameError`。这类 bug 在真机上极难复现，
  但一旦出现就是"数据错乱"，必须防住。
- **`truncate` 用例断言"半截帧不能被当成有效帧"**：客户端检查帧尾必须是 `\r\n`，
  否则按帧错误重试。这是最容易漏的一条——很多框架 `readline` 拿到啥就解析啥。

## 五、指标

```
用例 55　通过 55　失败 0　跳过 0
协议分支覆盖 15/15
命令 521 条　重试 11　超时 9
时延 P50 4.47ms　P95 5.7ms　max 54.77ms
```

- **分支覆盖 15/15**：9 条命令成功路径 + 5 个错误码 + 超时，协议定义的路径全部走到。
- **P50 4.47ms**：模拟器按 MCU 处理一条 AT 指令建模为 `latency_ms=4.0` 并叠加 ±25% 抖动，
  实测中位数 4.47ms 与模型一致——说明时延统计链路本身是准的（这点见下一节踩坑）。
- **max 54.77ms**：`slow` 故障注入故意延迟 350ms 造成的长尾，属预期。

## 六、踩过的坑：时延一开始被量成 15ms

第一版报告显示 P50 ≈ 15ms，但模拟器里明明写的 `latency_ms=4.0`。查了三轮：

1. 怀疑 `time.sleep()` 粒度不够 → 加了日志，确认 sleep 实际睡够了；
2. 怀疑 Windows 定时器精度 → 加了 `timeBeginPeriod(1)`，没变化；
3. **真正原因：`time.monotonic()` 在 Windows 上底层是 `GetTickCount64`，分辨率 15.6ms。**

后果不只是"读数偏大"：`readline()` 的等待循环里 `now` 一直不前进，
`deadline - now` 永远大于 0，循环空转到超时，既烧 CPU 又把测量值抬高 3 倍多。

改成 `time.perf_counter()`（高精度计数器）后，P50 从 ~15ms 降到 4.46ms，与模型吻合。
顺带保留了 `timeBeginPeriod(1)`：`perf_counter` 精度够，但 `sleep` 仍受系统时钟粒度影响，
提精度能让"等 1ms"真的等 1ms。

> 这段留在 README 里是有意的。**时延是设备测试的核心指标，量错了等于没测**；
> 能讲清楚"为什么错、怎么定位、怎么修"，比报一个好看的数字更可信。

## 七、运行

```bash
# 1) 模拟器模式（默认，无需硬件、无需 pyserial）
python run.py

# 2) 真实串口（需 pip install pyserial）
python run.py --port COM3 --baud 115200

# 3) 只跑某一组
python run.py -k fault
python run.py -k boundary -v

# 4) 标准 pytest 用法也支持
pytest tests -q
```

依赖：Python 3.9+、pytest。**pyserial 不是硬依赖**，只有接真机才需要——这样默认路径零配置可跑。

跑完产出：

- `output/report.html` — 自包含报告（内联 SVG 环形通过率 + 分套件条形 + 用例明细 + 分支覆盖），单文件可直接发给 HR
- `output/summary.json` — 机器可读结果，供 CI 断言

## 八、诚实的边界

这个项目能证明什么、不能证明什么，说清楚比藏着好：

- **模拟器是自研的，不是真实固件。** 它证明的是**测试框架的设计能力**（分层、可插拔后端、
  故障注入、指标采集），不是"我测过某厂商的真实设备"。协议是我按 AT 指令风格定义的，
  不是任何一家厂商的真实协议。
- **`SerialDevice` 走的是标准 pyserial 读写，未在真实板子上做过长时间验证**——
  真机上还要处理 DTR/RTS 时序、波特率协商、设备枚举等，这些是后续要补的。
- **故障注入是"计划式"的**（`faults=[...]` 队列按序消费），不是随机概率注入。
  好处是**可复现**（固定种子 + 固定顺序），代价是覆盖不到"随机时刻出错"的场景。
- 分支覆盖统计的是**协议定义的路径**，不等于代码行覆盖，也没有做 MC/DC。
